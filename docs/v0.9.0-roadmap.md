## 1. Executive Summary & Strategic Vision

### 1.1 Strategic Vision

StudyFrog is a Linux-native desktop workstation engineered for self-directed scholars, researchers, and professional certification candidates. It transforms a local directory of CommonMark files into an integrated learning ecosystem combining spaced retrieval practice, visual knowledge synthesis, psychometric analytics, authentic examination drills, and local machine intelligence.

Where traditional spaced repetition tools (such as Anki) treat learning as an isolated parade of disconnected flashcard atoms, and personal knowledge management outliners (such as RemNote and Logseq) entangle notes in proprietary databases or fragile block trees, StudyFrog asserts that **effective learning requires a continuous, bidirectional bridge between deep document synthesis and atomic retrieval practice—without sacrificing user data sovereignty or computing performance.**

StudyFrog v0.9.0 marks the transition from an advanced flashcard and rehearsal engine to a **complete, autonomous cognitive operating system**. The release focuses squarely on eliminating the friction points that cause students to abandon spaced repetition systems: review backlog paralysis, fragmented document-to-card workflows, rigid linear card presentations, and reliance on remote commercial APIs for intelligent synthesis.

### 1.2 The Four Inviolable Pillars of v0.9.0

1. **Local-First Data Sovereignty**: Plain Markdown vault files with YAML front-matter and 26-character ULID identities remain the sole authoritative source of truth. SQLite (`.studyfrog/index.sqlite`) stores strictly derived search indexes, graph layouts, and transactional history. Zero cloud accounts, zero telemetry, zero forced background network egress.
2. **Zero Inherent Impls (Design Principle P1)**: All domain types are plain data structures. No `impl Struct` gives a type behavior. Operational behavior is encapsulated strictly within free functions taking `&T` or `&mut T`. Trait implementations serve exclusively as single-line non-logic delegations.
3. **Strict Modularity & File Size Guardrail (Design Principle P6)**: Every `.rs` file in the workspace adheres to a strict hard cap of $\le 250$ lines. Code complexity is governed by clear functional decomposition across acyclic crate boundaries.
4. **Permanent Offline Intelligence**: AI capabilities must function entirely on consumer hardware without active internet connectivity or paid API subscriptions. Generative capabilities must never crash the host application or degrade the desktop GUI's 60 FPS responsiveness.

### 2.2 In-Depth Subsystem Technical Analysis

#### 2.2.1 SRS Rehearsal Engine & Scheduling Algorithms

StudyFrog v0.8.0 implements dual scheduling algorithms in `crates/studyfrog-srs`: the modern Free Spaced Repetition Scheduler (FSRS-6) and the classic SuperMemo-2 (SM-2) algorithm, coupled with an orthogonal Familiarity tempering factor and a strictly pure rehearsal state machine in `crates/studyfrog-rehearsal`.

```
                    +------------------------------------+
                    |       REHEARSAL STATE MACHINE      |
                    |    (studyfrog-rehearsal::step)     |
                    +------------------------------------+
                                      │
                         Input: Action::Rate(Rating)
                                      ▼
             +───────────────────────────────────────────────────+
             │             Scheduling Algorithm Engine           │
             │                (crates/studyfrog-srs)             │
             +───────────────────────────────────────────────────+
                     │                                   │
                     ▼                                   ▼
          +─────────────────────+             +─────────────────────+
          |       FSRS-6        |             |        SM-2         |
          |  (fsrs.rs:11-48)    |             |   (sm2.rs:26-57)    |
          |  R(t) = (1+c*t/S)^d |             |  EF' = EF + delta   |
          |  I = S/c*(R^(1/d)-1)|             |  I_n = I_{n-1} * EF |
```

##### 1. FSRS-6 Mathematical Implementation (`crates/studyfrog-srs/src/fsrs.rs`, `src/params.rs`)
The FSRS-6 algorithm operates purely over memory Stability ($S$) and Difficulty ($D$). Given review rating $g \in \{1: \text{Again}, 2: \text{Hard}, 3: \text{Good}, 4: \text{Easy}\}$ and elapsed interval $t$ in days:
- **Parameters & Derived Constants (`params.rs:4-39`)**:
  Published FSRS-6 default weights comprise a 21-parameter array (`DEFAULT_WEIGHTS: [f32; 21]`):
  $$w = [0.212, 1.2931, 2.3065, 8.2956, 6.4133, 0.8334, 3.0194, 0.001, 1.8722, 0.1666, 0.796, 1.4835, 0.0614, 0.2629, 1.6483, 0.6014, 1.8729, 0.5425, 0.0912, 0.0658, 0.1542]$$
  The forgetting curve exponent is derived from the final parameter:
  $$\text{decay} = -w_{20} = -0.1542$$
  The curve factor is dynamically computed to guarantee $R(S, S) = 0.90$:
  $$\text{factor} = 0.9^{1/\text{decay}} - 1 = 0.9^{-1/0.1542} - 1 \approx 0.9845$$
- **Retrievability Decay**:
  $$R(t) = \left(1 + \text{factor} \cdot \frac{t}{S}\right)^{\text{decay}}$$
- **Interval Calculation for Target Retention ($R_{\text{req}}$)**:
  $$I(S, R_{\text{req}}) = \frac{S}{\text{factor}} \cdot \left(R_{\text{req}}^{1/\text{decay}} - 1\right)$$
  When $R_{\text{req}} = 0.90$, $R_{\text{req}}^{1/\text{decay}} - 1 = 0.9^{1/\text{decay}} - 1 = \text{factor}$, meaning the calculated interval precisely equals the stability $S$:
  $$I(S, 0.90) = \frac{S}{\text{factor}} \cdot \text{factor} = S$$
- **Stability Updates**:
  - Initial stability: $S_0(g) = w_{g-1}$ where initial weights are $[w_0, w_1, w_2, w_3] = [0.212, 1.2931, 2.3065, 8.2956]$.
  - Successful recall ($g \ge 2$):
    $$S' = S \cdot \left(1 + \exp(w_8) \cdot (11 - D) \cdot S^{-w_9} \cdot \left(\exp((1 - R) \cdot w_{10}) - 1\right)\right)$$
  - Lapsed recall ($g = 1$, Again):
    $$S' = w_{11} \cdot D^{-w_{12}} \cdot \left((S + 1)^{w_{13}} - 1\right) \cdot \exp((1 - R) \cdot w_{14})$$
  - Intervals are clamped to a hard upper bound of $36,500$ days ($100$ years) (`params.rs:18`, `schedule.rs:59`).

##### 2. SM-2 Algorithm Implementation (`crates/studyfrog-srs/src/sm2.rs`)
The classic SuperMemo-2 engine maps ratings as Again $\to 1$, Hard $\to 3$, Good $\to 4$, Easy $\to 5$:
- **Ease Factor (EF) Recalculation**:
  $$EF' = \max\left(1.3, \; EF + \left(0.1 - (5 - g) \cdot (0.08 + (5 - g) \cdot 0.02)\right)\right)$$
- **Interval Progression**:
  $$I_1 = 1, \quad I_2 = 6, \quad I_n = \lceil I_{n-1} \cdot EF' \rceil \quad (\text{for } n \ge 3)$$
  In `crates/studyfrog-srs/src/sm2.rs:44`, intervals for $n \ge 3$ are computed using `(previous as f32 * ease).ceil() as u32` rather than rounding, guaranteeing strict monotonic growth and avoiding zero progression for small multipliers. On grade $g < 3$ (failure), repetition count resets to $0$ and the interval resets to $1$ day (`sm2.rs:51-57`).

##### 3. Familiarity Factor Schedule Tempering (`crates/studyfrog-srs/src/familiarity.rs`)
StudyFrog v0.8.0 features a unique **Familiarity Factor** ($F \in [0.0, 1.0]$) that tempers calendar review intervals without corrupting the underlying FSRS/SM-2 memory model:
- **Default Parameters (`FactorParams` via `factor_params_default()`)**:
  `strength = 2.0`, $S_{\text{half}} = 30.0 \text{ days}$, bounds = $[0.25, 2.0]$, and `full_at_review = 4`.
- **Expected Familiarity**:
  $$F_{\text{expected}}(S) = \frac{S}{S + S_{\text{half}}}$$
- **Dynamic Strength Scaling ($\beta$)**:
  $$\beta = \text{strength} \cdot \text{ramp}(\text{reviews}, p)$$
  where $\text{ramp}(\text{reviews}, p)$ applies zero strength up to review 2 and ramps linearly to $1.0$ at `full_at_review` ($4$ reviews) (`familiarity.rs:42-46`).
- **Interval Multiplier**:
  $$m = \exp\left(\beta \cdot \left(F - F_{\text{expected}}(S)\right)\right)$$
  clamped strictly to $[0.25, 2.0]$. When $\beta = 0.0$, $m = 1.0$.
- **Exam Deadline Pacer**: When an exam date $t_{\text{exam}}$ approaches, familiarity scales the interval so items are reviewed precisely before the test deadline rather than overshooting it (`familiarity.rs:72-77`).

##### 4. Rehearsal State Machine & Queues (`crates/studyfrog-rehearsal/src/session.rs`, `step.rs`)
The rehearsal session is encapsulated in `Session` (`session.rs:21-46`):
```rust
pub struct Session {
    pub run: Run,
    pub queue: Vec<Uid>,
    pub cursor: usize,
    pub phase: ItemPhase,
    pub shown_at_ms: u32,
    pub paused_at_ms: Option<u32>,
    pub paused_in_item_ms: u32,
    pub started_ms: u32,
    pub paused_total_ms: u32,
    pub last_t_ms: u32,
    pub next_seq: u32,
    pub requeues: HashMap<Uid, u8>,
}
```
In strict compliance with Design Principle P2 (functional purity), time is passed explicitly as discrete millisecond integers (`shown_at_ms: u32`, `started_ms: u32`, `last_t_ms: u32`). Non-deterministic system clock calls (`Instant::now()`) are completely barred from the state machine. Requeue frequency per item is tracked deterministically in `requeues: HashMap<Uid, u8>`.

State progression is strictly pure: `step(session, input) -> Result<(Session, Vec<Effect>), StepError>`. Item phases transition deterministically:
$$\text{NoItem} \longrightarrow \text{Shown} \longrightarrow \text{Revealed} \longrightarrow \text{Advance (Cursor += 1)}$$
If `requeue_again = true`, items rated Again are automatically appended to the queue tail (`step.rs:175-187`).
The queue ordering subsystem (`crates/studyfrog-rehearsal/src/queue/order.rs:57-93`) supports 7 distinct mathematical sort orders: `Due`, `Sequential`, `HardestFirst`, `EasiestFirst`, `StalestFirst`, `LeastFamiliar`, and `LowestRetrievability`.

#### 2.2.2 Item Models, Typed Arenas, & Markdown Parsing

##### 1. Domain Data Models (`crates/studyfrog-core/src/items.rs`, `src/meta.rs`, `src/arena.rs`)
All entities are identified by 26-character Crockford Base32 Universally Unique Lexicographically Sortable Identifiers (`Uid`, wrapping `ulid::Ulid`).
- `Meta`: Encapsulates `uid: Uid`, `title: String`, `tags: Vec<String>`, `aliases: Vec<String>`, `created: CivilDateTime`, `updated: CivilDateTime`.
- `Note`: Long-form study note comprising `meta`, `stack: Idx<Stack>`, `rehearse_title: bool`, and CommonMark `body: String`.
- `Card`: Atomic flashcard comprising `meta`, `stack: Idx<Stack>`, `reversible: bool`, `front: String`, and `back: String`.
- `Question`: Open-ended assessment item comprising `meta`, `stack: Idx<Stack>`, `prompt: String`, `reference: String`, `accepted: Vec<String>`, `rubric: Vec<String>`, and `min_score: f32` (default 0.70).
- `Stack`: Container hierarchy holding `meta`, `description: String`, and `settings: StackSettings`.

Entities are stored in typed contiguous memory arenas (`Arena<Note>`, `Arena<Card>`, `Arena<Question>`, `Arena<Stack>`) indexed by zero-cost typed handles `Idx<T>`. This data-oriented architecture guarantees zero cache misses during queue compilation and strictly prevents dangling reference cycles without requiring reference counting (`Rc<RefCell<T>>`).

##### 2. Markdown Parsing & Lossless Preservation (`crates/studyfrog-md/src/doc.rs`, `src/sections.rs`)
- **Sections Separator (`???`)**: Prompt and answer sections are parsed using the explicit separator `???`. Everything preceding `???` is rendered as the question/prompt; everything following represents the answer/reference text.
- **Lossless YAML Frontmatter Extra-Key Preservation**: The parser utilizes `serde-saphyr` to parse document headers. Unrecognized frontmatter keys are preserved verbatim in an ordered vector `extra: Vec<RawEntry>` (`doc.rs:12-18, 77`). When StudyFrog rewrites an edited card or note to disk, third-party YAML properties (e.g. Obsidian metadata, Git sync timestamps) are round-tripped losslessly without byte loss.
- **Cloze & Image Occlusion Syntax**:
  - Cloze deletions: Parsed via `cloze.rs` supporting `{{c1::target::hint}}` syntax.
  - Image occlusion: Parsed via `occlusion.rs` supporting coordinate bounding boxes over local image assets.

```
|  [Exam Plan Construction] ──> Restrict items strictly to Card & Question (Notes rejected)        |
|                               Set ScheduleEffect::PracticeOnly, Disable Requeue-on-Again          |
|                                                                                                   |
|  [Strict Progression]     ──> Forbid Action::Flip, Action::Skip, Action::Mark, Action::Rate       |
|                               Mandatory typed student response; Empty answers rejected            |
|                                                                                                   |
|  [Locked Commit]          ──> Submitting answer permanently locks response; No going back;        |
|                               Instant cursor increment (session.cursor += 1)                      |
|                                                                                                   |
|  [Offline Semantic Grade] ──> Candle MiniLM (Cosine Sim) evaluates answer against rubric/accepted|
|                                                                                                   |
|  [Academic Grading Band]  ──> Clamped in tenths of percent against German/International scales    |
|                               Pass threshold fixed at 60.0% (Grade D / 4.0)                       |
+---------------------------------------------------------------------------------------------------+
```

- **Strict Progression Rules**: The state machine rejects `Action::Flip`, `Action::Skip`, `Action::Mark`, or `Action::Rate`. The student *must* type their answer. Submitting an answer immediately commits the grade and advances the cursor (`session.cursor += 1`). No review, backtracking, or re-answering is permitted.
- **Combined German and International Grading Scale**:
  Total percentage score $P = \frac{\sum \text{score}_i}{\sum \text{max\_score}_i} \times 100\%$ maps to standardized academic bands (`exam.rs:8-40`):
  - `APlus` / `1+` (95.0% – 100.0%)
  - `A` / `1.0` (90.0% – 94.9%)
  - `AMinus` / `1.3` (85.0% – 89.9%)
  - `BPlus` / `1.7` (80.0% – 84.9%)
  - `B` / `2.0` (75.0% – 79.9%)
  - `BMinus` / `2.3` (70.0% – 74.9%)
  - `C` / `3.0` (65.0% – 69.9%)
  - `D` / `4.0` (60.0% – 64.9%, **Minimum Pass Threshold**)
  - `F` / `5.0` (< 60.0%, **Failed**)
  Calculations are clamped in tenths of a percent to prevent floating-point edge discrepancies (`exam.rs:46-57`).

#### 2.2.5 Study Diary & Metacognitive Calibration

##### 1. Psychometric Diary Data Model (`crates/studyfrog-core/src/diary.rs`)
- `DiaryEntry`: Captures civil `Date`, optional `study_minutes: Option<u32>`, freeform markdown reflections `content: String`, and a map of psychometric ratings.
- **13 Standard Psychometric Rating Scales (`diary.rs:11-25`)**:
  `performance`, `success`, `confidence`, `effort`, `focus`, `energy`, `difficulty`, `satisfaction`, `understanding`, `mood`, `stress`, `motivation`, and `sleep`.
  Scales accept integer ratings ($1$ to $5$) or categorical descriptive labels.

##### 2. Relational Storage Schema (`crates/studyfrog-store/src/diary.rs`, `src/schema_diary.rs`)
Persisted across normalized SQLite tables: `diary_entries`, `diary_runs`, `diary_stacks`, `diary_items`, `diary_exams`, and `diary_tags`. Enables bidirectional queries connecting subjective emotional states to objective review histories (`diary_query.rs:14-17`).

##### 3. Metacognitive Calibration Analytics (`crates/studyfrog-report/src/calibration.rs`)
Correlates subjective confidence ratings ($1$–$5$) recorded in the diary against empirical FSRS retrieval accuracy across identical study dates. Computes the **Metacognitive Calibration Index (MCI)** ($\Delta$):
$$\Delta = \frac{1}{N} \sum_{i=1}^N \left(\frac{\text{Confidence}_i - 1}{4} - \text{Accuracy}_i\right)$$
Categorized strictly in `crates/studyfrog-report/src/calibration.rs:101-105`:
- $\Delta > +0.05$: **Overconfidence Bias** (`CalibrationBias::Overconfident`, illusion of competence, learner overestimates recall probability).
- $\Delta < -0.05$: **Underconfidence / Impostor Bias** (`CalibrationBias::Underconfident`, unwarranted anxiety, excessive over-study).
- $-0.05 \le \Delta \le +0.05$: **Well Calibrated** (`CalibrationBias::WellCalibrated`, metacognitive alignment within $\pm 5\%$).

### 2.3 Architectural Invariants & Verification Baseline

StudyFrog enforces four foundational design constraints defined in `docs/DESIGN_PRINCIPLES.md` and verified by automated repository check scripts:

1. **Design Principle P1: Zero Inherent Impls (`scripts/check-impls.sh`)**
   - Structs are plain data bags. No `impl Struct` gives a type behavior.
   - Behavior lives in free functions taking `&T` or `&mut T`.
   - Trait implementations (`impl Trait for Type`) are permitted *only* as single-line bindings delegating directly to a free function.
   - *Verification*: AST parser in `tools/repo-lint/src/impls.rs` scans all `.rs` files. Result: `check-impls: ok (no inherent impl blocks)`.

2. **Design Principle P6: File Size Guardrail ($\le 250$ Lines/File) (`scripts/linecount.sh 250`)**
   - Target ~150 lines, hard ceiling of 250 lines per `.rs` file workspace-wide.
   - Enforces single-responsibility design; complex modules are partitioned into cohesive sub-units.
   - *Verification*: `scripts/linecount.sh 250`. Result: `linecount: ok (no .rs file over 250 lines)`.

3. **Design Principle P9 & P8: Safety & Decoupled Dependency DAG (`scripts/check-deps.sh`)**
   - Unsafe code is forbidden workspace-wide (`unsafe_code = "forbid"`).
   - Domain crates never depend on `ui` or `app`.
   - *Verification*: Manifest dependency audit in `scripts/check-deps.sh`. Result: `check-deps: ok`.

4. **Persistence Strategy (ADR 0003)**
   - Markdown files in the filesystem are the sole authoritative source of truth.
   - Deleting `.studyfrog/index.sqlite` causes zero data loss; the scanner rebuilds the index automatically on startup.

5. **Test Suite Execution Invariant: Linux Minimum Stack Size (`RUST_MIN_STACK=8388608`)**
   - Running the full workspace integration test suite on Linux (`cargo test --workspace`) requires setting `RUST_MIN_STACK=8388608` (8 MB stack).
   - Deep immediate-mode widget call trees in `studyfrog-ui` integration tests (specifically `tests/mcp_client_ui.rs`) exceed the standard 2 MB default Linux thread stack during full UI rendering tree evaluations.
   - *Verification*: Running `RUST_MIN_STACK=8388608 cargo test --workspace` produces 100% test passes across all 22 workspace crates.

### 2.4 Critical Limitations of v0.8.0

Despite its architectural maturity, the audit reveals five major engineering bottlenecks in v0.8.0 that form the primary impetus for v0.9.0:

1. **No Built-In Offline Generative SLM**: While `studyfrog-candle` runs `all-MiniLM-L6-v2` for 384-dimensional vector embeddings, it has no generative language model. All intelligent assistant features (flashcard authoring, oral exam coaching, vault synthesis) depend on external network APIs or a user-installed Ollama daemon. Offline users have no generative assistance out of the box.
2. **Review Backlog Paralysis**: When a user returns to StudyFrog after an absence, they face an insurmountable backlog (e.g. 800 overdue reviews). Categorical priority chips (Low, Medium, High) lack continuous mathematical ranking or daily queue budget slicing, leading to cognitive overwhelm and system abandonment.
3. **Fragmented Document-to-Card PDF Workflow**: PDF text highlights link to pages (`file.pdf#page=N`), but the system lacks rectangular lasso area cropping (essential for anatomical diagrams, chemical reactions, and mathematical proofs) and lacks 1-click split-screen contextual jumping during review.
4. **Absence of 2D Spatial Knowledge Synthesis**: StudyFrog provides an SoA force-directed link graph and a Kanban board, but lacks an open 2D spatial learning board (mind-map/concept canvas) for clustering notes, cards, and diagrams.
5. **Static Global FSRS Parameters**: `crates/studyfrog-srs/src/params.rs` hardcodes default FSRS-6 weights. The system lacks an offline optimization pass to fit parameters to the user's personal review history in SQLite.

1. **Anki (v24+)**: The dominant open-source flashcard tool. 4. **Logseq**: Local-first, block-based outliner built in ClojureScript. Features integrated PDF annotation with rectangular area crops, converting highlights into blocks. However, its in-memory Datalog query engine suffers severe performance degradation on large vaults (>5,000 blocks), and its flashcard system is an unoptimized SM-2 implementation.
5. **Quizlet**: Mass-market commercial study tool optimized for rapid onboarding and cramming. Features intuitive two-column entry, "Match Mode" (rapid tile matching), and auto-generated multiple-choice exams. However, it operates on a closed cloud model with aggressive paywalls, heavy telemetry, zero plain-text ownership, and has abandoned long-term scientific spaced repetition.
6. **SuperMemo 18 (SM-18)**: The algorithmic origin of spaced repetition (Piotr Wozniak). Features the two-component SM-18 memory model (Stability and Retrievability), universal forgetting curve matrices, continuous priority queues ($0.0\%$ to $100.0\%$), and Incremental Reading (IR). However, it is an archaic, Windows-only Delphi application with proprietary binary storage (`.kno`, `.dat`) and extreme UI hostility.
7. **MarginNote 3/4**: Academic workstation for macOS/iPadOS. Integrates split-screen PDF reading with an infinite 2D mind-map canvas. Lassoing text or diagrams creates excerpt nodes that can be merged across textbooks and converted into flashcards. Clicking a card jumps directly to the source page and bounding box. However, it is locked to Apple platforms, relies on closed SQLite databases, uses basic Leitner scheduling, and lacks Markdown interoperability.

### 3.3 Concrete Functional Gaps: Leaderships & Deficits

#### Gaps Where StudyFrog Leads Competitors:
1. **Metacognitive Self-Assessment & Diary Calibration**: StudyFrog is the only learning environment with a structured 13-scale learning diary that calibrates subjective learner confidence against objective FSRS retrieval accuracy to expose cognitive biases (overconfidence/underconfidence).
2. **Behavioral Chronobiology & Fatigue Diagnostics**: Neither Anki, Obsidian, nor RemNote provide hour-of-day/day-of-week performance analytics or within-session cognitive fatigue decay curves.
3. **Rigorous Native Exam Simulation with Local SLM Semantic Grading**: StudyFrog v0.8.0 provides an authentic examination environment with mandatory written answers evaluated offline by an embedding model (`studyfrog-candle`), complete with academic letter/percentage grading bands.
4. **Autonomous AI Interoperability via MCP & FrogScript**: First-class Model Context Protocol (MCP) server/client and a sandboxed DSL (`studyfrog-script`) eliminate the security hazards of Anki's unconstrained Python monkey-patching.

1. **Visual Spatial Knowledge Synthesis (Obsidian Canvas / MarginNote)**: Obsidian Canvas and MarginNote provide infinite 2D spatial whiteboards where students visually cluster notes, cards, and diagrams, drawing relational arrows. 6. **Seamless Inline Card Delimiters in Notes (RemNote / Obsidian)**: In RemNote and Obsidian, writing `Term::Definition` anywhere in a note instantly registers an active recall card without creating separate files or invoking extraction dialogs. ### 4.2 Quantization Formats & Numerical Precision

1. **GGUF (GPT-Generated Unified Format) with Q4_K_M (Recommended)**:
   - Utilizes k-quantization with variable block bit-depth: critical attention projection tensors ($W_q, W_k, W_v$) retain 5-bit or 6-bit precision, while massive feed-forward matrices ($W_{\text{gate}}, W_{\text{up}}, W_{\text{down}}$) are compressed to 4-bit.
   - Result: Average bit-depth of ~4.5 bits/weight. Degrades perplexity by $<0.05$ compared to unquantized FP16, while reducing memory footprint by ~70% (from 3.1 GB to 980 MB).
   - Supports zero-copy memory mapping (`mmap`), enabling sub-second cold starts.
2. **Q8_0 (8-bit Quantization)**: Lossless compared to FP16, but requires ~1.7 GB disk and ~2.2 GB RAM, reducing CPU inference throughput by 40% on memory-bandwidth-constrained hardware.
3. **SafeTensors / AWQ / GPTQ**:
   - SafeTensors (unquantized FP16) requires ~3.1 GB disk space and lacks optimized CPU SIMD kernels.
   - AWQ and GPTQ are tailored for CUDA/ROCm matrix-multiplication units and perform poorly on consumer x86_64 AVX2/AVX-512 pipelines.

### 4.3 Architectural Trade-Off Analysis: In-Process Rust vs. Managed Local Sidecar

#### 1. In-Process Rust Inference (`candle`, `burn`, `llama-cpp-rs`, `mistral.rs`)
- *Candle*: Pure Rust (already in `studyfrog-candle` for MiniLM embeddings). However, autoregressive text generation in Candle lacks optimized quantized CPU kernels (AVX-512, AMX, ARM NEON microkernels), generating tokens at roughly 40–50% the speed of `llama.cpp`. Context management and KV-cache tiling must be maintained manually in Rust.
- *Critical Build Gate Discovery (ADR 0004 lines 58–60)*:
  > *"The runtime lives in its own crate, `studyfrog-candle`, which only the application binary depends on; the application passes its loader to the UI. This keeps the tensor library out of every other crate and test binary (linking it into each UI test made the gate take about 40 minutes)."*
  Expanding Candle to full autoregressive LLM decoding would reinflate test linking times and compile overhead across the workspace.
- *Process Blast Radius*: If an in-process generative model encounters an Out-Of-Memory (OOM) condition or panics during matrix multiplication, the entire StudyFrog GUI process terminates instantly, risking data loss in open tabs.
- *Memory Retention (Lack of Idle Reclaim)*: Standard Linux memory allocators (`glibc malloc`, `jemalloc`) retain heap pages due to fragmentation. Dropping an in-process model does not return 1.5 GB of RAM to the OS kernel.

#### 2. Managed Local Background Sidecar Process (RECOMMENDED)
- *Architecture*: StudyFrog manages a dedicated headless background sidecar binary (`llama-server`) driven via local loopback IPC.
- *Total Fault Isolation*: The sidecar runs in an isolated child process. An OOM or crash cannot kill the StudyFrog GUI. The supervisor catches process termination, logs the event, and gracefully alerts the user.
- *100% Idle RAM Reclamation*: When the assistant is idle for 5 minutes, the supervisor cleanly terminates the sidecar (SIGTERM). The operating system kernel immediately reclaims all 1.4–2.5 GB of RAM. While studying flashcards or reading PDFs, StudyFrog maintains its lean 30–50 MB memory footprint!
- *Cross-Platform Lifecycle Supervision & Stdin EOF Watchdog*:
  - To prevent runaway zombie processes without relying on platform-exclusive syscalls (such as Linux-only `PR_SET_PDEATHSIG`, which does not exist on macOS Darwin), the supervisor establishes a parent-to-child standard input pipe (`Stdio::piped()`).
  - When the parent GUI process terminates (whether normally, via SIGKILL, or unexpected segfault), the OS kernel automatically closes the parent's write-end of the pipe. The child `llama-server` detects `EOF` on `stdin` and immediately terminates itself. This watchdog operates 100% cross-platform in safe Rust, preserving `unsafe_code = "forbid"`.
  - For defensive depth, auxiliary cleanup handles OS-specific hooks (`PR_SET_PDEATHSIG` on Linux, `kqueue NOTE_EXIT` watchdog on macOS).
- *Safe Startup PID Reaping*:
  - The supervisor writes the child PID to `<app_home>/run/assistant.pid`.
  - On startup, to clean up stale processes from a power loss without causing dangerous PID-reuse race conditions (accidentally killing an innocent process after PID rollover), the supervisor strictly inspects the process executable path (`/proc/<pid>/exe` on Linux, `proc_pidinfo` on macOS) to verify that it matches `llama-server` before issuing termination signals.
- *Secure Ephemeral Authentication*:
  - The loopback API is protected with an ephemeral bearer token.
  - To prevent exposing the token in `ps aux` or `/proc/<pid>/cmdline`, the token is passed strictly via the `LLAMA_API_KEY` environment variable in `std::process::Command::env` rather than CLI flags.
- *Zero Build-Time Bloat & Zero Unsafe Code*: The main Rust binary never links massive C++ tensor compilation pipelines. Test suite compilation remains sub-second, and `unsafe_code = "forbid"` is preserved workspace-wide.

### 4.5 Architectural Compatibility & Design for StudyFrog

### 4.5 Architectural Compatibility & Design for StudyFrog

#### 1. The Core Trait & Data Hierarchy
In strict adherence to Design Principles P1 (Zero Inherent Impls) and P5 (Trait Minimization), traits are reserved exclusively for polymorphic interfaces with multiple interchangeable backends (`AssistantBackend`, `ModelProvider`). Plain data containers with single implementations (such as conversation state) remain pure structs:

```rust
// Trait 1: Backend process lifecycle supervision
pub trait AssistantBackend: Send + Sync {
    fn status(&self) -> BackendStatus;
    fn start(&mut self, config: &BackendConfig) -> Result<(), BackendError>;
    fn stop(&mut self) -> Result<(), BackendError>;
    fn is_ready(&self) -> bool;
}

// Data Model 2: Plain data container for session & conversation history (P1/P5 compliant)
#[derive(Debug, Clone, PartialEq)]
pub struct AssistantSession {
    pub session_id: String,
    pub history: Vec<Message>,
    pub created_ms: u32,
    pub updated_ms: u32,
}

// Trait 3: Text completion provider (single-shot & thread-safe streaming)
pub trait ModelProvider: Send + Sync {
    fn model_name(&self) -> &str;
    fn complete(&self, req: &CompletionRequest) -> Result<CompletionResponse, ProviderError>;
    fn complete_streaming(
        &self,
        req: &CompletionRequest,
        token_sender: std::sync::mpsc::Sender<StreamChunk>,
    ) -> Result<(), ProviderError>;
}

// Thread-safe stream chunk delivered across background worker threads to egui UI
#[derive(Debug, Clone, PartialEq)]
pub enum StreamChunk {
    Thinking(String),
    Token(String),
    Complete(String),
    Error(String),
}
```

*Thread-Safe Streaming Design*: In `crates/studyfrog-ui/src/runtime.rs`, asynchronous model operations execute on background worker threads (`std::thread::spawn`). Passing a borrowed reference `&mut dyn StreamingCompletionHandler` cannot cross thread boundaries. By using `std::sync::mpsc::Sender<StreamChunk>`, tokens and status updates are sent asynchronously to the egui event loop, which wakes the UI thread with `ctx.request_repaint()` for stutter-free 60 FPS text rendering.

#### 2. Design Principle P1 Compliance (Zero Inherent Impls)
All structs are plain data containers. Operational logic is implemented in pure free functions taking `&T` or `&mut T`. Trait implementations are single-line delegations:

```rust
// Plain data struct
pub struct ManagedSidecar {
    pub supervisor: SidecarSupervisor,
}

// Free functions contain all operational logic
pub fn sidecar_status(sup: &SidecarSupervisor) -> BackendStatus { /* ... */ }
pub fn sidecar_start(sup: &mut SidecarSupervisor, cfg: &BackendConfig) -> Result<(), BackendError> { /* ... */ }
pub fn sidecar_stop(sup: &mut SidecarSupervisor) -> Result<(), BackendError> { /* ... */ }
pub fn sidecar_is_ready(sup: &SidecarSupervisor) -> bool { /* ... */ }

// Trait implementation is pure single-line delegation
impl AssistantBackend for ManagedSidecar {
    fn status(&self) -> BackendStatus {
        sidecar_status(&self.supervisor)
    }
    fn start(&mut self, config: &BackendConfig) -> Result<(), BackendError> {
        sidecar_start(&mut self.supervisor, config)
    }
    fn stop(&mut self) -> Result<(), BackendError> {
        sidecar_stop(&mut self.supervisor)
    }
    fn is_ready(&self) -> bool {
        sidecar_is_ready(&self.supervisor)
    }
}
```

#### 3. Design Principle P6 Compliance ($\le 250$ Lines/File) & Crate Boundary Enforcement
In strict compliance with ADR 0001, ADR 0009, and `scripts/check-deps.sh` (`[agent]="core"`, `[net]="agent"`), networking and SQLite persistence are decoupled from `studyfrog-agent`. The SLM subsystem is partitioned across 11 cohesive files across their proper architectural crates, each strictly under 250 lines:

**A. `crates/studyfrog-agent/` (Pure Data Protocols & Process Supervision — Depends only on `core`)**:
1. `crates/studyfrog-agent/src/assistant_backend.rs` (~65 LOC): `AssistantBackend` trait and status enums.
2. `crates/studyfrog-agent/src/assistant_session.rs` (~75 LOC): Plain data struct `AssistantSession` and pure session functions.
3. `crates/studyfrog-agent/src/model_provider.rs` (~90 LOC): `ModelProvider` trait and `StreamChunk` channel types.
4. `crates/studyfrog-agent/src/sidecar_types.rs` (~85 LOC): Plain configuration data: `SidecarConfig`, `SidecarStatus`, `PortRange`.
5. `crates/studyfrog-agent/src/sidecar_supervisor.rs` (~160 LOC): Supervisor state machine, heartbeat polling, idle timer tracking.
6. `crates/studyfrog-agent/src/sidecar_process.rs` (~145 LOC): `std::process::Command` child spawning, cross-platform stdin pipe watchdog, and signal termination.
7. `crates/studyfrog-agent/src/model_catalog.rs` (~120 LOC): Supported models catalog, SHA-256 hashes, GGUF URLs, and licensing metadata.

**B. `crates/studyfrog-net/` (HTTP Transport & Model Downloader — Links `ureq` and depends on `agent`)**:
8. `crates/studyfrog-net/src/sidecar_client.rs` (~150 LOC): Loopback HTTP client via `ureq` and Server-Sent Events (SSE) streaming chunk parser.
9. `crates/studyfrog-net/src/model_download.rs` (~170 LOC): Chunked HTTP downloader with HTTP Range resumption, SHA-256 validation, and progress reporting.

**C. `crates/studyfrog-store/` & `crates/studyfrog-service/` (RAG Storage & Pipeline Orchestration)**:
10. `crates/studyfrog-store/src/rag_store.rs` (~140 LOC): SQLite table schema (`vault_embeddings`), vector BLOB storage, and cosine similarity query routines.
11. `crates/studyfrog-service/src/rag_pipeline.rs` (~160 LOC): Vault note chunking, MiniLM embedding generation via `studyfrog-candle`, CPU prompt budgeting, and RAG context assembly.

#### 4. Local-First Vault, CPU Prompt Budgeting & On-Device RAG Pipeline
- **Zero Remote Network Egress**: The sidecar binds strictly to `127.0.0.1` on an ephemeral port with an ephemeral bearer token passed via `LLAMA_API_KEY`. No network traffic leaves the machine.
- **On-Device Retrieval-Augmented Generation (RAG)**:
  - SQLite table `vault_embeddings (item_id TEXT, chunk_idx INTEGER, text TEXT, vector BLOB)` stores 384-dimensional dense vectors generated by `studyfrog-candle` (`all-MiniLM-L6-v2`).
  - When the user asks a question, StudyFrog computes the query embedding, executes sub-15ms cosine ranking over local vault embeddings, and retrieves relevant note passages.
- **CPU Time-To-First-Token (TTFT) Mitigation & Strict Prompt Budgeting**:
  - *The Prefill Bottleneck*: On a consumer 4-core x86 CPU, prompt evaluation speed (`pp` / prefill phase) for a 1.5B model is ~100–160 tokens/second. Unconstrained RAG injection (2,000+ tokens) results in **12 to 18 seconds of silence** before the first token is emitted, frustrating users and appearing frozen.
  - *Strict Prompt Budgeting*: `studyfrog-service` enforces a hard ceiling of $\le 1,024$ total prompt tokens:
    - System prompt & instructions: $\le 150$ tokens.
    - Conversation history: sliding window capped to $\le 150$ tokens (last 1–2 turns).
    - RAG context injection: strictly capped to $\le 768$ tokens (top-2 to top-3 highest-scoring concise snippets, max 250 tokens each).
  - *Latency Outcome*: Evaluating $\le 1,024$ prompt tokens limits prefill latency to **under 3.5–5.0 seconds** on 4-core x86 CPUs (and $<1.0$ second on Apple Silicon), followed immediately by 20–35 t/s streaming generation.
  - *UX State Transition*: While prefill is running, the UI displays a distinct **"Thinking / Analyzing vault..."** pulsing progress indicator. The moment the first token chunk arrives, the UI seamlessly transitions into real-time token streaming.

For commercial or strictly open deployments requiring 3B capacity, `SmolLM2-1.7B-Instruct` (Apache 2.0) and `Llama-3.2-3B-Instruct` (Llama Community License) are provided as fully permissible alternatives.
2. **Four-Tier Fallback Hierarchy**:

4. **1-Click Model Download Manager**: Integrated into `Assistant > Settings` in `studyfrog-net` with download progress bars, HTTP Range resume capability, and SHA-256 verification.
5. **Streaming Generation UX**: Token-by-token streaming in Chat and Exam views via Server-Sent Events (SSE) with "Thinking / Analyzing vault..." prefill feedback.

#### Epic 1: FrogCanvas (2D Spatial Mind-Map & Concept Board)
- **Objective**: Provide an infinite 2D spatial learning board where students visually arrange, cluster, and link cards, notes, and PDF excerpts.
- **Data Model**: `_canvas.toml` files stored in stack directories:
  ```toml
  version = 1
  [[nodes]]
  id = "01JA7X1..."
  kind = "Item"
  item_id = "01JA7W9..."
  x = 120.0
  y = -450.0
  width = 240.0
  height = 160.0
  color = "emerald"

  [[edges]]
  id = "01JA7Y2..."
  from = "01JA7X1..."
  to = "01JA7X2..."
  label = "causes"
  direction = "Forward"
  ```
- **Implementation**: `crates/studyfrog-graph` manages SoA spatial index and force-directed auto-layout; `crates/studyfrog-ui/src/views/canvas_view.rs` renders nodes, edges, and grouping frames in egui with spatial quadtree culling.

#### Epic 2: PDF Precision Area Cropping & 1-Click Split-View Navigation
- **Objective**: Allow students to crop rectangular regions from PDFs into visual cards and jump instantly between review cards and source documents.
- **Data Model**: Frontmatter coordinate anchor: `source: textbooks/histology.pdf#page=84&bbox=150,220,500,480`.
- **Implementation**: Lasso tool in `crates/studyfrog-pdf/src/crop.rs` renders crop rectangles; Rehearsal/Detail view renders a 1-click split jump button that opens the PDF viewer in a side-by-side pane, scrolls to page 84, and flashes the bounding box. Extracted crop regions are stored in an LRU memory and disk rasterization cache to eliminate frame hitches when rapidly reviewing cards at 60 FPS.

#### Epic 3: Continuous Priority Queue & Anti-Paralysis Slicing
- **Objective**: Prevent review backlog abandonment by assigning every card a continuous numerical priority ($0.0\%$ to $100.0\%$) and slicing daily queues to a manageable budget.
- **Algorithm**:
  $$\text{EffectivePriority}(c) = w_p \cdot \text{Priority}(c) + w_r \cdot (1 - R(t)) + w_f \cdot (1 - F(c))$$
  Pure function in `crates/studyfrog-srs/src/priority_slice.rs` sorts the due queue by effective priority and truncates to the user's configured session budget (e.g. 30 cards).

#### Epic 4: Gamified & Multi-Modal Active Recall (Match Mode & Distractor Exams)
- **Objective**: Provide low-friction active recall drills for evening study and enhance exam preparation with automated multiple-choice tests.
- **Implementation**:
  - *Match Mode*: Interactive $3 \times 4$ tile pairing grid in `crates/studyfrog-rehearsal/src/match_mode.rs` and `crates/studyfrog-ui/src/views/match_grid.rs` with monotonic timing and streak counters.
  - *Distractor Exams*: Multiple-choice question generator in `crates/studyfrog-rehearsal/src/distractor.rs` extracting semantically plausible distractors via `studyfrog-candle` MiniLM embeddings (`all-MiniLM-L6-v2` cosine nearest-neighbor search) from the active stack or vault, rather than naive random sibling shuffling.

#### Epic 5: Algorithmic Optimization & Frictionless Capture (FSRS Auto-Tuning & Inline Cards)
- **Objective**: Personalize FSRS-6 parameters using local review history and enable inline card creation in notes without modal popups.
- **Implementation**:
  - *FSRS Auto-Tuner*: Pure Rust Adam gradient descent / coordinate descent optimization routine in `crates/studyfrog-srs/src/optimizer.rs` minimizing log-loss across all 21 parameters over SQLite `reviews` records with L2 regularization shrinking toward `DEFAULT_WEIGHTS` priors.
  - *Inline Delimiters*: Scanner in `crates/studyfrog-md/src/inline_cards.rs` parsing `Term :: Definition` lines into virtual cards in SQLite.

#### Epic 6: Offline Local SLM Internal Assistant (Managed Sidecar, Qwen2.5-1.5B, Local RAG)
- **Objective**: Deliver a fully offline, zero-telemetry generative assistant for card generation, oral exams, and vault Q&A.
- **Implementation**: Managed local sidecar supervisor in `crates/studyfrog-agent` running `Qwen2.5-1.5B-Instruct` (Q4_K_M) with 5-minute idle shutdown, cross-platform stdin watchdog, SSE streaming with "Thinking / Analyzing vault..." prefill feedback, CPU prompt budgeting ($\le 1,024$ tokens), and local vault RAG via `studyfrog-store` and `studyfrog-candle` embeddings.

### 5.3 Comprehensive Risk Register & Mitigation Strategies

| Risk ID | Description & Potential Impact | Likelihood | Impact | Architectural Mitigation Strategy |
|---|---|---|---|---|
| **RSK-01** | **FrogCanvas Rendering Degradation**: Large concept boards (>1,000 nodes) cause frame drops in egui during zoom/pan or "Zoom to Fit". | Medium | High | Implement spatial quadtree culling in `studyfrog-graph` for off-screen nodes. For full-board zoom-out (where all nodes are in viewport), implement multi-tier Level-of-Detail (LOD) rendering: collapse nodes to plain colored rects and hide text glyphs when zoom $< 0.40\times$, and use batched mesh geometry (`Shape::mesh`) to eliminate per-element immediate-mode paint calls. |
| **RSK-02** | **SLM Child Process Zombies & Stale PID Signaling**: Sidecar process remains running if parent crashes, or startup PID reaping signals an innocent process due to PID rollover. | Medium | High | Implement cross-platform parent-to-child stdin pipe EOF watchdog (child exits when parent closes stdin; safe Rust, zero unsafe code). Auxiliary OS cleanup via `PR_SET_PDEATHSIG` (Linux) and `kqueue NOTE_EXIT` (macOS). Safe PID reaping inspects executable path (`/proc/<pid>/exe` on Linux, `proc_pidinfo` on macOS) before signaling. Ephemeral bearer token passed via `LLAMA_API_KEY` environment variable. |
| **RSK-03** | **Model Download Failures**: Large 980 MB GGUF download fails on slow or unstable connections. | High | Medium | Implement HTTP Range requests in `studyfrog-net` for resumable chunked downloads. Validate final file integrity against cryptographic SHA-256 hashes in `model_catalog.rs`. |
| **RSK-04** | **PDF Coordinate System Discrepancies**: Bounding boxes misalign across different display DPRs and zoom levels. | Medium | Medium | Store all bounding boxes in normalized coordinates ($0.0 \dots 1.0$ relative to page width and height) rather than absolute screen pixels or PDF points. Cache rasterized crops in LRU buffer to eliminate frame hitches. |
| **RSK-05** | **FSRS Optimizer Overfitting & High-Dimensional Stagnation**: Tuning 21 parameters on small review logs (<500 reviews) produces unstable intervals or optimization diverges. | High | Medium | Employ Adam gradient descent with finite-difference gradients and L2 regularization shrinking toward `DEFAULT_WEIGHTS` priors (rejecting Nelder-Mead due to simplex collapse in $D > 10$). Require $\ge 500$ reviews before unlocking optimization. |
| **RSK-06** | **Inline Card Collision with Markdown**: `Term :: Definition` syntax collides with standard Markdown colons. | Low | Low | Require strict delimiter spacing (` :: ` with whitespace on both sides) and ignore colons inside code blocks, math environments, or table headers. |
| **RSK-07** | **Hardware Variability & Unsupported CPU Instructions**: Older x86 CPUs lacking AVX2 or ARM systems lacking FP16 dotprod instructions crash `llama-server` with `SIGILL`; low-RAM systems (<6 GB) trigger system OOM. | Medium | High | Implement CPU feature detection in `studyfrog-agent` (`is_x86_feature_detected!("avx2")`) and available RAM capacity probing before sidecar launch. Provide automatic graceful fallback to `SmolLM2-360M` or Tier 3 (Lexical / Heuristic mode). |
| **RSK-08** | **Context Length KV-Cache RAM Scaling & Prefill Latency**: Large context windows (>4k tokens) inflate KV-cache RAM linearly ($O(N)$) and attention computation quadratically ($O(N^2)$), causing RAM $>2.5$ GB and CPU freezes. | High | High | Enforce strict CLI parameter `--ctx-size 4096` in sidecar supervisor, support 8-bit KV-cache quantization (`-ctk q8_0 -ctv q8_0`), and enforce hard prompt budgeting in `studyfrog-service` ($\le 1,024$ total tokens, $\le 768$ RAG context) with "Thinking..." UI feedback. |
